# CLAUDE.md

Guidance for any Claude Code (or other AI agent) instance opening this repository, on this device or a new one.

## Project

**QA Automation framework** for the *Regplus World Tax Analyzer (WTA)* web app, built with **Python + pytest + Playwright (sync API)**, using the **Page Object Model (POM)**.

Goal: comprehensive, evidence-rich, visually-observable regression coverage of the live application — every assertion is real, every locator comes from inspecting the actual DOM, and every run produces a professional HTML report a non-engineer can read.

This is the **single, permanent workspace** for this project. Do not create a second project/folder for a new feature or run — inspect and extend the files already here.

**Read [AGENT.md](AGENT.md) before starting work.** It's the full handbook (application behavior, architecture, execution rules, troubleshooting, maintenance) kept portable across machines/sessions. This file (`CLAUDE.md`) stays the fast per-module reference; `AGENT.md` has the cross-cutting rules and the "why" behind them. Keep both current when either changes — don't let them contradict each other.

## Architecture (as it actually exists — read before assuming a generic layout)

```
config/settings.py       - all config, read from .env (never hardcode credentials)
                            also: APP_ORIGIN, timeouts, feature_dir() (parent-module path helper)
pages/                   - Page Object Model: one class per page/section
pages/wta/               - every page object for the WTA (World Tax Analyzer) parent module
pages/login_page.py      - platform-level, OUTSIDE wta/ (pre-product: the login page itself)
pages/landing_page.py    - platform-level, OUTSIDE wta/ (the post-login product picker)
utils/case.py            - Case: every test's step/action/click/fill/check helper
                            (red-highlights the live element + captures per-step evidence)
utils/highlight.py        - the red on-screen highlight
utils/session.py          - session-reuse: logs in once per run, caches storage_state
utils/auth.py             - perform_login(case, page): reuses the cached session
utils/screenshot.py       - final + per-step screenshot capture
utils/excel_utils.py      - writes test_data/<Feature>/ or test_data/WTA/<Feature>/
utils/report_utils.py     - builds the self-contained reports/automation_report.html
utils/dashboard.py        - the live HEADLESS=false execution dashboard
tests/<feature>/          - platform-level test dirs: login/, dashboard/
tests/wta/<feature>/      - every WTA feature's tests (information, pillar2, news, forms,
                            regulations, treaties, tools, calculator)
test_data/<Feature>/      - auto-generated Excel, platform-level features only (Login, Dashboard)
test_data/WTA/<Feature>/  - auto-generated Excel, every WTA feature — do not hand-author either
conftest.py               - session lifecycle, fixtures, report/Excel generation, security gate
run_tests.py              - the CLI entry point (use this, not bare `pytest`, for full runs)
```

**Parent module structure**: WTA (World Tax Analyzer) is one product among several the app offers (see the top-right tabs: Workspace / World Tax Analyzer / Transfer Pricing Analyzer / RegBriefings) — `pages/wta/`, `tests/wta/<feature>/`, and `test_data/WTA/<Feature>/` hold everything specific to it. `login`/`dashboard` sit OUTSIDE `wta/` at every level (`pages/login_page.py`, `pages/landing_page.py`, `tests/login/`, `tests/dashboard/`, `test_data/Login/`, `test_data/Dashboard/`) because they're the platform shell that exists before a product is even chosen — login, then the landing page where WTA itself gets picked. A future parent module (e.g. a `tpa` module for Transfer Pricing Analyzer) would get the exact same shape as a sibling of `wta`: `pages/tpa/`, `tests/tpa/<feature>/`, `test_data/TPA/<Feature>/`, registered in `run_tests.py`'s `FEATURE_PATHS` the same way `WTA_FEATURE_PATHS`/`"wta"` are. `config/settings.py::feature_dir(base, feature)` is the one shared rule every feature-keyed output directory (test_data, screenshots, logs) uses to decide platform-level vs. nested-under-its-parent-module — update `NON_WTA_FEATURES` there (or generalize it into a real module lookup) when a second parent module needs the same treatment.

`tests/login/` is the one exception to session reuse: it has its own `conftest.py` that forces a fresh, unauthenticated browser context per test, because it tests the login flow itself.

The **Treaties** module (`pages/wta/treaties_menu.py` + `pages/wta/treaties_*_page.py`, `tests/wta/treaties/`) covers the "Treaties" top-nav dropdown's 5 sub-pages: Full DTA, PE Clause, Other Articles, WHT Rates, MLI Data. Four of the five (Full DTA, PE Clause, Other Articles, WHT Rates) reuse `pages/wta/wta_common.py`'s single-select `JurisdictionPanel` (heading "Select Jurisdiction", placeholder "Use the left panel to choose jurisdiction.") and render a table only after a country is selected. MLI Data is the exception — no jurisdiction panel at all; its table is server-rendered on load and sorted via a `?sort=jurisdiction:asc|desc` URL query param, toggled by clicking its sortable column headers. Watch the same rsuite-dropdown gotcha documented in `pages/wta/pillar2_menu.py`/`pages/wta/treaties_menu.py`: EVERY top-nav dropdown's `<li class="rs-dropdown-item">` is mounted in the DOM at once (hidden, not removed), so an unscoped `page.locator("li.rs-dropdown-item")` after opening one dropdown returns items from every dropdown — filter to `.is_visible()` (or scope tightly by exact text) rather than assuming a raw count/list reflects only the open menu.

**Known live application defect — nav viewport width**: the "Treaties", "Calculators", "Tools" and "BEPS" top-nav dropdowns are completely ABSENT from the DOM (not just hidden) below ~1600px viewport width, with no responsive/overflow fallback — confirmed 0 matches at 1440/1500px, 1 match at 1600/1700px, against this project's 1440x900 default viewport (`conftest.py`'s `browser_context_args`). This is a real, unfixed application defect, documented rather than hidden: any test suite covering one of these four dropdowns needs its own directory-local `browser_context_args` fixture override at 1680x900 (see `tests/wta/treaties/conftest.py` and `tests/wta/tools/conftest.py` — both apply the identical override for this identical reason). Follow this same pattern for any future module behind one of these four dropdowns.

The **Tools** module (`pages/wta/tools_menu.py`, `pages/wta/tools_projects_page.py`, `pages/wta/tools_questionnaire_creator_page.py`, `tests/wta/tools/`) covers the "Tools" top-nav dropdown's 2 sub-pages: **Projects** (`/wta/Project`, a real project-management workspace — create/rename/delete projects, each holding a table of saved items) and **Questionnaire Creator** (`/wta/QuestionnaireCreator`, a rich-text questionnaire builder — click tree questions to insert them into a Syncfusion editor, "Start Over" to reset with a confirm dialog, "Add to Project" to save into a Projects workspace). Distinct gotcha from Treaties: neither Tools page supports a direct full-page deep link — `page.goto()` straight to `/wta/Project` or `/wta/QuestionnaireCreator` redirects to `/wta/Information` instead (no server-side SPA route for a hard link), so unlike every Treaties page object, the Tools page objects have no `goto()` — `pages/wta/tools_menu.py::ToolsMenu.open_item()` (click through the dropdown) is the only supported way in, and this is asserted as real, documented application behavior in `tests/wta/tools/test_tools_navigation.py::test_toolsmenu_03_...`, not silently worked around. Projects tests create only uniquely-named, self-cleaning test data (`ToolsQA_<tag>_<timestamp>`, deleted again before the test ends) since this is a real shared account with dozens of pre-existing projects from prior manual/automation use.

**Open issue confirmed 2026-10-15 against RC specifically**: `pages/wta/tools_questionnaire_creator_page.py::click_question()` clicks a tree question but the editor never receives the content on RC — directly verified by polling the editor's `innerHTML` for 20s straight after the click (stayed empty the whole time), which cascades into all 4 of this feature's regression tests failing (`Start Over`/`Add to Project` stay disabled since the editor has no content to act on). Not yet checked against Staging/Live. See `AGENT.md` section 7a for the full writeup.

The **Calculator** module (`pages/wta/calculator_menu.py` + `pages/wta/calculator_*_page.py`, `tests/wta/calculator/`) covers the "Calculators" top-nav dropdown's 6 real sub-pages: **Corporate Rate Finder** (`/wta/CorpRateFinder`, done), **Repatriation Calculator** (`/wta/RepCalculator`, done), **WHT Router** (`/wta/WhtRouter`, done), **Loss Relief Calculator** (`/wta/LossCalculator`, done), **CIT Calculator** (`/wta/CitCalculator`, done), **Interest And Penalties** (`/wta/InterestAndPenalties`, done) — all 6 sub-pages now covered. Confirmed live via `.is_visible()` filtering, same rsuite-dropdown gotcha as Treaties/Tools/Pillar 2. The sheet of reference test cases provided for this module bundles Corporate Rate Finder's test IDs under a "Repatriation Calculator" prefix even though they are two separate menu items/pages; treat sheet-provided test groupings as a starting point for business understanding, not ground truth for the actual UI structure. Same no-deep-link quirk as every Tools page (confirmed for all 6 URLs): no `goto()` on any Calculator page object, reach them only via `CalculatorMenu.open_item()`. Same viewport defect as Treaties/Tools/BEPS — `tests/wta/calculator/conftest.py` applies the identical 1680x900 override.

**WHT Router** specifically (`pages/wta/calculator_wht_router_page.py`): no provided QA-sheet rows exist for this module (built entirely from live DOM discovery). Same "By Jurisdiction" / "By Entity" mode pair and rsuite `SelectPicker` shape as Repatriation Calculator (`_ensure_open()`/`open_and_pick()` copied verbatim - same `aria-expanded` React render-commit race). Selecting the 3rd required field (Source Jurisdiction/Income Stream/Residence Jurisdiction, whichever is picked last) auto-fires `POST https://regplusnest.api.kaz.com.bd/api/WhtRouter` - NOT gated behind the "Calculate" button click, which just re-confirms/re-renders the already-fetched result. **Calculation-validation anchor**: Australia (source) → Singapore (residence) → Portfolio Dividend returns `{"bestRate": 15.0, "domesticRate": 30.0, "treatyRate": 15.0}` from the live API - confirmed this endpoint is PUBLIC/unauthenticated (a direct unauthenticated `requests.post` returns 200), unlike `tools_projects_page.py`'s Project API which needs the browser's own JWT - so tests call it directly rather than needing `page.expect_response()`. This is the same underlying AU/SG Portfolio Dividend treaty already documented as Repatriation Calculator's Treaty Rate=15.00% anchor. Results render as a real `<table>` (`<tr><td>Best Rate</td><td>15%</td></tr>`, confirmed via HTML dump), not a div-based layout. **Real gotcha**: unlike Repatriation Calculator, Generate Memo/Get Forms/Add to Project are entirely ABSENT from the DOM before a result exists (not merely disabled) - `count() == 0`, not `is_disabled()`. The "Intermediaries 1"/"Intermediaries 2" (optional) rows each open an "Intermediate Streams and Jurisdictions" modal with independent Streams/Countries checklists; its checkboxes are the `<label for="...">`'s PRECEDING SIBLING `<input>`, not a descendant (same shape as `pages/landing_page.py::category_checkbox`) - a `label.locator("input")` lookup times out silently. Same-country selection shows a blocking `.rs-modal-wrapper` reading "Please select different Source Jurisdiction and Residence Jurisdiction." (Cancel-only) - same validation family as Repatriation Calculator, different exact wording.

**Loss Relief Calculator** specifically (`pages/wta/calculator_loss_relief_page.py`): no provided QA-sheet rows exist for this module either. Different downstream shape from every other Calculator sub-page: no second jurisdiction/company, no `Calculate` button, and NO Generate Memo/Get Forms/Add to Project row anywhere - every field recalculates live, client-side, as you type. A Tax Year select appears after Source Jurisdiction, with real date-range options ("01 July 2023 - 30 June 2024"), followed by a page-specific "Mode" radio pair - Ordinary loss relief (default, 13 fields) / Capital loss relief (9 fields) - each a completely different field set. **Calculation-validation anchor** (pure arithmetic, no API involved, independently reproducible in Python): entering Losses brought forward=1000, Tax losses in current period=500, Losses actually offset=300 live-computes Brought forward losses available=1,000, Total Losses available=1,500, Losses available for offset=1,500, Losses available for carry forward=1,200, Total losses carried forward=1,200 - each exactly matching simple addition/subtraction across the chain (see page object docstring for the full formula). **Real gotcha confirmed live**: the page's 4 `input[type='radio']` elements are NOT interleaved by visual row - `[0]` By Jurisdiction, `[1]` By Entity, `[2]` Ordinary loss relief, `[3]` Capital loss relief - indexing them by assumed row order silently reads the wrong radio. **Another real gotcha**: in Capital loss relief mode, two of its 9 fields share the EXACT SAME visible label text ("Capital losses in current year"), so they must be targeted by their 1-based position among the page's `input[class*='reg-input']` elements, not by label text (see `LossReliefPage.capital_field(n)`). "Start over" shows the identical confirmation dialog as WHT Router ("Are you sure to reset all your selections?", Cancel/Yes) - its text isn't visible in a `body.inner_text()` snapshot taken without first waiting for the modal, which can make a reset look like a silent no-op if you don't check for the dialog explicitly.

**CIT Calculator** specifically (`pages/wta/calculator_cit_page.py`, on-page heading "Corporate Income Tax Calculator"): no provided QA-sheet rows exist for this module either. Reuses Corporate Rate Finder's own `CORPORATE_RATE_API` (`GET .../api/CorporateRate?country=<CODE>&year=<YEAR>` - note the query param is `country`, not Corporate Rate Finder's own `countryCodes`) for its headline rate, so it hits the exact same null-`HeadlineRate` data gap and uses the SAME confirmed-good anchor: Bangladesh + tax year 2024 (HeadlineRate=55.00). Selecting a jurisdiction/year with no rate data (e.g. Australia/2023-2024) shows a blocking modal reading "No data found for this jurisdiction. You may try for another jurisdiction." (Cancel-only). **Real gotcha confirmed live**: the computed fields (Taxable domestic income, Total CIT, Total tax due, Nominal ETR, etc.) only recalculate on BLUR of the Taxable Income field, not on every keystroke - `press_sequentially()` alone leaves them empty; always blur (e.g. `.press("Tab")`) before asserting on any computed value. **Calculation-validation anchor**: Bangladesh/2024-2025/Taxable Income=100,000 (no exemptions) computes Total CIT=55,000, Total tax due=55,000.00, Nominal ETR=55 - exactly 100,000 x 55%, independently re-fetchable via the same API rather than compared to the UI itself. Action buttons (Generate Memo/Get Forms/Add to Project) are present but disabled from the start (same pattern as Repatriation Calculator, NOT WHT Router's "absent until a result exists" pattern). **Another real gotcha**: this module's own By Entity mode labels its company field "Entity in Residence states" - NOT "Source Company" like WHT Router/Loss Relief Calculator's By Entity mode - don't assume a shared label across Calculator sub-pages' By Entity flows.

**Interest And Penalties** specifically (`pages/wta/calculator_interest_penalty_page.py`, on-page heading "Interest and Penalty Calculator"): no provided QA-sheet rows exist for this module either, the last of the 6 Calculator sub-pages built. "Type of offences" is disabled showing "No offenses available" for most jurisdiction/year combinations (its own `GET .../api/InterestPenalty?countryCode=<CODE>&year=<YEAR>` returns `AllOffense: null`, same data-gap spirit as Corporate Rate Finder/CIT Calculator) - confirmed for Australia/2023 AND Bangladesh/2024. **This module's own confirmed-good anchor is Bangladesh + tax year 2023** (a DIFFERENT year than Corporate Rate Finder's/CIT Calculator's Bangladesh/2024 anchor - don't assume the same year works across modules), which has one real seeded offence "Late payment" with a "Per day penalty" (`PenaltyPerDay=100000`, footnote "Test"). **Real, live-confirmed application CRASH**: typing a comma-containing string into either date field (`press_sequentially("October, 01, 2026", ...)`) crashes the entire React app to a generic "Oops! Something went wrong" error screen - the "MMMM, dd, yyyy" placeholder is a format HINT for the picker's masked input, not literal text to type. Always use the calendar GUI instead (`InterestPenaltyPage.pick_date()`), never type into these fields. Calendar day cells are `role="gridcell"` with a ZERO-PADDED `aria-label="DD Mon YYYY"` (e.g. `"01 Oct 2026"`, not `"1 Oct 2026"`). **Calculation-validation anchor** (purely arithmetic): Bangladesh/2023-2024/Late payment/Tax due=1,000/01 Oct 2026 to 11 Oct 2026 computes Total days overdue=10, Total penalty amount=Total interest and penalty=1,000,000 (= PenaltyPerDay x days, confirmed live), Outstanding tax due=1,000 (no advance payment) - independently recomputed in Python from the known PenaltyPerDay, not compared to the UI itself.

**Corporate Rate Finder** specifically (`pages/wta/calculator_rate_finder_page.py`): both the country list AND the year list are multi-select (unlike every single-select Treaties `JurisdictionPanel` page), rendering one results-table ROW per selected year and one COLUMN per selected country. A country's column-header name opens a same-page `.rs-modal-wrapper` ("Corporate rate details for `<Country>`"), not a new page/tab, contradicting the reference sheet's wording for that case — live behavior was followed, not the sheet. **Real, live-confirmed data gap**: `HeadlineRate` is `null` for the large majority of country/year combinations (checked across AU/IN/CN/SG/JP/US/CA/DE and multiple years) — the results table legitimately renders an empty rate cell in that case; this is documented, asserted application behavior (`CRF_09`), not hidden. One confirmed live exception is used as this module's calculation-validation anchor: Bangladesh + tax year 2024 has a real `HeadlineRate` of `55` (footnote "This for the testingg .." — evidently seeded test data), independently re-fetched from `GET https://regplusnest.api.kaz.com.bd/api/CorporateRate?countryCodes=BD&year=2024` in `CRF_07` and compared against the UI's rendered value, rather than comparing the UI against itself.

**Repatriation Calculator** specifically (`pages/wta/calculator_repatriation_page.py`): two modes ("By Jurisdiction" / "By Entity") share the same downstream flow once resolved to two countries. All its dropdowns are rsuite `SelectPicker`s (`role="combobox"`, not the checkbox-list `JurisdictionPanel`); `row_combobox(label)` finds one by its table row. **Real gotcha worth repeating for any future rsuite-`SelectPicker` work**: that component's `aria-expanded` attribute is NOT a reliable "is it open" signal — it can still read `"false"` for a brief moment right after a genuinely successful click (a React render-commit race), so code that re-clicks to "ensure open" based on that attribute can silently re-close an already-open picker. `RepatriationCalculatorPage._ensure_open()` checks whether the listbox's `[role='option']` children are actually visible instead. **Calculation-validation anchor**: AU (source) → SG (residence) → Dividends → 7% holding resolves to a Treaty Rate of 15.00% (cross-checked against `GET /api/Treaty?hostCountryCode=AU&partnerCountryCode=SG`); the Exchange Rate field is a real, user-entered multiplier (NOT auto-fetched), and with amount=100,000 the computed Withholding tax amount/Total Tax Due both equal exactly `amount x rate% x exchangeRate` — independently recomputed in Python and compared to the UI, not UI-vs-UI. **Real negative-validation modals**: picking the same country for both jurisdictions blocks with "Source and Residence Jurisdiction must be different." (Cancel-only); an entity pair (By Entity mode) whose countries have no treaty shows a DIFFERENT, informational "No treaty rate is available between `<A>` and `<B>`. Only domestic rate will apply." (also Cancel-only, but the calculation proceeds on the domestic rate). **The "Add to Project" dialog has TWO required fields that are easy to conflate**: `input[name='project']` ("Project Name" — the actual new project's name) and a SEPARATE `input[name='name']` ("Title" — the saved item's own title) — both inputs share the same (duplicate, invalid) `id="name"`, so `id`-based lookups are ambiguous; only `name` distinguishes them. Submitting fires `POST .../api/Project/AddToProject` → `{"isSuccess":true}` (a third, distinct response shape from the Tools-documented Create/Rename/Delete shapes). **`page.request.*` calls bypass this app's auth entirely** (it's a JWT bearer token read from `localStorage`, not a cookie `page.request` would send) and get a silent `401` — any direct API verification/cleanup must go through the browser's own authenticated call (`page.expect_response(...)` around the triggering click) or reuse an existing in-app UI flow (e.g. `pages/wta/tools_projects_page.py::ProjectsPage` for cleanup), never a bare `page.request.get/post(...)`.

**Session-cache gotcha discovered while building Calculator**: `utils/session.py::_state_is_valid()` only checks that the post-login URL isn't `/auth/login` — if the cached JWT in `.auth/state.json` has expired, the app can still briefly serve `/wta/Information` at that URL before/without redirecting, so a stale-but-"valid-looking" session can pass this check and then fail unpredictably deep in a test (e.g. the top-nav "Calculators"/"Treaties"/etc. button never renders, every `get_by_role("button", name=...)` on it times out at 30s). If a whole feature suddenly fails at its very first navigation step with no other symptom, delete `.auth/state.json` and re-run before assuming the new code is wrong.

**Cross-environment stale-session bug, fixed automatically (2026-10-16)**: a real incident confirmed this exact gotcha going further than expected — a cached session left over from RC was silently reused while `.env` pointed at Live (different origin entirely, not just an expired JWT), and because the app didn't land cleanly back on `/auth/login` for the mismatched origin, `_state_is_valid()`'s own probe still passed, so every single test in a 245-test run hung for its full timeout budget before failing, one after another. Fixed in `utils/session.py::_cached_state_matches_current_env()`: before even opening a browser context, it compares the cached state file's own recorded `origin`/cookie domain against the current `.env`'s `APP_ORIGIN`, and treats a mismatch as invalid - triggering an automatic fresh login instead of a slow cascade of confusing timeouts. Manually deleting `.auth/state.json` after an environment switch is no longer required, though still harmless if done out of habit.

**Slow-environment timeout tuning (2026-10-14/15)**: `DEFAULT_TIMEOUT_MS`/`ASSERTION_TIMEOUT_MS` were raised from 15000 to 60000 after confirming live that a newly-added account/environment can take up to ~60s for real content to render after a cached-session cold reload, even though the app's own "Syncing with Enterprise Cloud" banner clears from the DOM within 1-4s (not a reliable ready signal). Any raw `locator.wait_for(...)`/`page.evaluate(...)` call that bypasses `Case.click()`/`Case.fill()`/`Case.verify_visible()` skips these centralized timeouts entirely and will fail on a slow environment regardless of this fix — always route through `Case`. Full detail and the exact fix pattern: `AGENT.md` section 3 "Timeouts".

**Windows venv-launcher pair, not a duplicate run**: on Windows with Python 3.11+, a single `.venv\Scripts\python.exe ...` invocation normally shows as TWO `python.exe` processes (a near-idle launcher stub plus the real worker interpreter) — confirmed by checking `ExecutablePath`/`ParentProcessId` via `Get-CimInstance Win32_Process`. Don't mistake this for a concurrent-run collision and kill it; see `AGENT.md` section 0/7 for how to tell them apart from a genuine duplicate.

**`utils/cleanup.py` `onexc` bug (fixed 2026-10-15)**: its locked-file handler used the deprecated `onerror` 3-tuple convention (`exc_info[1]`) while registered as `shutil.rmtree`'s newer `onexc` callback, which (Python 3.12+) passes the exception instance directly — crashing the "gracefully skip a locked file" handler itself and taking down the whole run before a single test executed. Fixed to read `exc_info` directly. Full detail: `AGENT.md` section 3.

## RegBriefings (a parent module sibling to WTA)

**RegBriefings** (`pages/regbriefings/`, `tests/regbriefings/<feature>/`, `test_data/RegBriefings/<Feature>/`) is a second parent module alongside WTA — one of the 4 top-level product tabs (Workspace / World Tax Analyzer / Transfer Pricing Analyzer / **RegBriefings**, see `pages/landing_page.py`), NOT a WTA top-nav dropdown. Confirmed live it has **no viewport-width defect** (visible at the project's default 1440x900, unlike WTA's Treaties/Calculators/Tools/BEPS dropdowns), so no directory-local `browser_context_args` override is needed for any RegBriefings suite. Run just this module with `python run_tests.py --feature regbriefings` (the dedicated single-command entry point, registered the same way `--feature wta` is). Clicking the "RegBriefings" tab lands on `/regbrief/home/myBriefings` ("My Briefs"); the left sidebar then offers 6 items: **My Briefs** (done), World Tax Brief, Transfer Pricing Brief, Tax Treaty Brief, Archive, Preferences.

**Real gotcha confirmed live, applies to every RegBriefings page object**: the sidebar items are plain `<span>` text wrapped in an `<a>` with NO `href` attribute, so `get_by_role("link", ...)` never matches (times out silently) — use `get_by_text(name, exact=True)` instead. On the aggregated "My Briefs" page specifically, that text locator alone is AMBIGUOUS (strict-mode violation: "Tax Treaty Brief" matches the sidebar span plus 2 `<h6>` section headings elsewhere on the page) — `RegBriefingsNav`'s nav locators all scope with `.first` (the sidebar's own element is reliably first in DOM order). **Unlike WTA's Tools/Calculator sub-pages, every RegBriefings sub-page supports a direct full-page deep link** (confirmed live for all 4 real routes) — same pattern as Treaties, not Tools/Calculator's menu-only restriction. "Preferences" is the one exception: clicking it opens an OVERLAY MODAL, not a route change (confirmed live: the URL doesn't change) — it must be closed (via its "Cancel" button, to avoid altering the real account's settings) before any other sidebar item becomes clickable again, or subsequent clicks silently timeout against the still-open overlay intercepting pointer events.

**My Briefs** specifically (`pages/regbriefings/my_briefs_page.py`): the RegBriefings landing/dashboard view. Aggregates ONE section per brief type (World Tax Brief / Transfer Pricing Brief / Tax Treaty Brief) the logged-in account has subscribed to via Preferences — **confirmed live this is account-specific, NOT always all 3**: the RC/Staging test accounts show all 3 sections, but the Live account (`monir.smh@gmail.com`) has only "Tax Treaty Brief" checked in Preferences and so shows only that one section on My Briefs. Tests must never hardcode "all 3 sections always present" — `MyBriefs_03` instead reads the real Preferences checkbox state first, then verifies My Briefs shows exactly those sections, making the test genuinely environment/account-agnostic rather than tuned to one account's data. Each section has its own "Print" button and its news items end in a real "Full Story in Regfollower" link. A fixed short wait after opening the tab is NOT enough on a slower account/environment (same class of gotcha as WTA's `ASSERTION_TIMEOUT_MS` writeup) — wait for the account-independent "Quick Access" heading instead of any one brief-type section before asserting anything.

## Project rules & conventions

- **Strict Page Object Model**: every locator lives in `pages/`, never inline in a test. Locators must come from inspecting the real live DOM (a throwaway Playwright discovery script is the standard way to do this in this repo) — never guessed.
- **Prefer explicit, resilient locators**: `get_by_role`, `get_by_label`, `get_by_text`, `get_by_alt_text`, stable `#id`/`name` attributes. Avoid absolute XPath, `nth-child`, or auto-generated class names unless there's no reliable alternative.
- **Test data stays out of test logic**: `.env` for credentials/config, `test_data/<Feature>/*.xlsx` for generated test case records (auto-written by `utils/excel_utils.py` from each run's results — don't hand-edit these files, they're regenerated every run).
- **Never hardcode credentials** anywhere in `pages/`, `tests/`, or committed files. Read them from `config/settings.py` (which reads `.env`). `.env` is gitignored; `.env.example` holds placeholders only.
- **Never weaken an assertion to force a pass.** If the live app genuinely misbehaves, that's a real, documented FAIL — fix the automation if the automation is wrong, but never soften the check that caught a real problem.
- **Every test uses `Case`** (`utils/case.py`) for its steps/actions/clicks/fills/checks — this is what drives the live red-highlight, the live dashboard, and the per-step evidence screenshots. Don't call raw `page.click()`/`page.fill()` in a test.
- **Every meaningful assertion has a human-readable message** via `case.check(text, ok, expected=..., actual=..., locator=...)`.
- **Keep `HEADLESS=false` as the default** in `.env` — the browser must stay visible unless explicitly overridden (`--headless` / `HEADLESS=true`).
- **Login/session reuse**: don't re-implement per-test login. Non-Login feature tests call `utils/auth.py::perform_login(case, page)`, which reuses the cached authenticated session (see `utils/session.py`) and only logs in for real if the cache is stale.
- **Reports/logs/screenshots are regenerated, not maintained by hand.** `run_tests.py` cleans the previous run's generated artifacts (screenshots, logs, report) before each run unless `--keep` is passed; it never touches source code, test cases, or docs.
- **Security**: the report build has a hard gate in `conftest.py` that raises if the plaintext `LOGIN_PASSWORD` ever appears in the generated HTML report — never bypass or remove this check.

## Commands

Full command reference: [ALL_COMMANDS.md](ALL_COMMANDS.md). The essentials:

```bash
python run_tests.py                     # full suite (the standard way to run this project)
python run_tests.py --feature login     # platform-level: login, dashboard
python run_tests.py --feature wta       # every WTA feature at once (the whole parent module)
python run_tests.py --feature calculator  # one WTA feature only - also: information, pillar2,
                                           # news, forms, regulations, treaties, tools
python run_tests.py --test LOGIN_05     # one specific Test Case ID
python run_tests.py --smoke             # @pytest.mark.smoke only
python run_tests.py --regression        # @pytest.mark.regression only
python run_tests.py --headed / --headless
python run_tests.py --keep              # skip pre-run cleanup of screenshots/logs/report
```

`python run_tests.py` is preferred over bare `pytest` because it also handles cleanup, headless/headed overrides, and prints the final report path — but `pytest tests/wta/calculator -v` (or any other path under `tests/`) works directly too when debugging a single file/directory.

After any run, the HTML report is at `reports/automation_report.html` (also auto-opened in the browser and printed as a `file://` link in the terminal).

## Adding a feature

See [ALL_COMMANDS.md](ALL_COMMANDS.md) > "Adding a Feature". In short, for a new WTA feature: page object in `pages/wta/`, tests in `tests/wta/<feature>/`, add the feature to `WTA_FEATURE_PATHS` in `run_tests.py`, then `python run_tests.py --feature <name>`. For a platform-level feature (not part of any product), the same pattern at the top level: `pages/`, `tests/<feature>/`, `FEATURE_PATHS`. For an entirely new parent module (a product sibling to WTA), see "Parent module structure" above.
